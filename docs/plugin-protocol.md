# Plugin protocol v1

This document defines `wuko.plugin/v1` without assuming a programming language or runtime. A
plugin is simply an executable named `wuko-plugin-<namespace>` that reads JSON messages from
standard input and writes JSON messages to standard output.

Protocol v1 remains supported unchanged. Steps that need managed-service lifetime or scoped calls
back into Wuko should opt into [plugin protocol v2](plugin-protocol-v2.md).

The distribution manifest and marketplace format are separate from this runtime protocol. See
[Executable plugins](plugins.md) for packaging, installation, discovery, and publishing.

## The protocol in five rules

1. Each message is one complete JSON object followed by a newline.
2. Wuko sends requests; the plugin returns exactly one response with the same string `id`.
3. The plugin may send output events before the final response.
4. Standard output is reserved for protocol messages. Write logs and diagnostics to standard error.
5. Wuko may have several requests in flight and may send a `cancel` notification at any time.

All examples below are single lines on the wire, even when displayed across several lines for
readability.

## Minimal plugin

A minimal plugin needs to answer `initialize`, implement its declared operations, and answer
`shutdown`. In language-neutral pseudocode:

```text
for each line from stdin:
    message = parse_json(line)

    if message.method == "cancel":
        cancel_work(message.params.id)
        continue

    try:
        if message.method == "initialize":
            result = {
                "protocol": "wuko.plugin/v1",
                "namespace": "hello",
                "steps": [{"type": "hello.uppercase"}],
                "executors": [],
                "helpers": []
            }
        else if message.method == "step.validate":
            result = {}
        else if message.method == "step.run":
            value = message.params.with.value
            result = {"outputs": {"value": uppercase(value)}, "variables": {}}
        else if message.method == "shutdown":
            write_json_line({"id": message.id, "result": {}})
            exit_successfully()
        else:
            raise_error("unsupported method")

        write_json_line({"id": message.id, "result": result})
    catch error:
        write_json_line({"id": message.id, "error": {"message": error.message}})
```

This synchronous loop is sufficient for quick operations. A plugin with long-running operations
must keep reading input while work is running so that it can receive cancellation and other
requests.

## Message envelopes

### Request

```json
{"id":"7","method":"step.run","params":{}}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Opaque request identifier generated by Wuko. |
| `method` | string | Method from the reference below. |
| `params` | object | Method parameters. It may be empty. |

Request IDs are unique within the plugin process. Do not interpret them as numbers.

### Successful response

```json
{"id":"7","result":{}}
```

### Error response

```json
{"id":"7","error":{"code":"invalid_config","message":"value is required"}}
```

A response must contain the matching `id` and exactly one of `result` or `error`. `message` is
required and is shown to the user. `code` is optional and reserved for machine-readable plugin
diagnostics; Wuko v1 does not interpret it.

The final response may arrive after responses for newer requests. Sending malformed JSON, an
unknown response ID, an unknown top-level frame field, or more than one final response for an ID
terminates the whole plugin connection.

### Stream event

During `step.run` or `executor.run`, a plugin may emit events before the final response:

```json
{"id":"7","event":"stdout","data":"aGVsbG8K"}
{"id":"7","event":"stderr","data":"d2FybmluZwo="}
{"id":"7","event":"started"}
```

`stdout` and `stderr` data is base64-encoded bytes. `started` has no data and tells Wuko that an
executor command has successfully started. Events use the request ID and must precede its final
response. Wuko ignores events for an operation after that operation is canceled.

### Cancellation notification

```json
{"method":"cancel","params":{"id":"7"}}
```

This is a notification, so it has no request ID and receives no response. The plugin should stop
the referenced work promptly and still send one final response for the original request. A
long-running plugin normally uses one reader loop plus independently cancellable jobs; writes to
standard output must remain serialized so frames cannot interleave.

## Initialization and declarations

Wuko initializes a process before using any operation:

```json
{"id":"1","method":"initialize","params":{"protocol":"wuko.plugin/v1","host_version":"v0.14.0"}}
```

`host_version` is optional and may be absent during installation verification. A plugin must use
`protocol` to decide whether the wire format is compatible. It may additionally require a minimum
host version for a documented host capability, but its versionless installation handshake must
remain side-effect free and successful.

A complete response looks like:

```json
{
  "id": "1",
  "result": {
    "protocol": "wuko.plugin/v1",
    "namespace": "acme",
    "lifecycle": true,
    "steps": [
      {"type": "acme.uppercase", "outputs": {"fields": {"value": {}}}},
      {"type": "acme.temporary", "cleanup": true}
    ],
    "executors": [
      {"type": "acme.local", "cancel_stops_process": true}
    ],
    "helpers": [
      {"name": "slug"}
    ]
  }
}
```

| Result field | Required | Meaning |
| --- | --- | --- |
| `protocol` | Yes | Must equal `wuko.plugin/v1`. |
| `namespace` | Yes | Must equal the namespace Wuko used to find the executable. |
| `lifecycle` | No | When true, enables `plugin.start` and `plugin.stop`. |
| `steps` | Yes | Namespaced step declarations. Use `cleanup: true` to receive `step.cleanup`; optional `outputs` declares a recursive result schema. |
| `executors` | Yes | Namespaced executor declarations. |
| `helpers` | No | Helper names exposed by explicitly declared workflow plugins. |

Step and executor types must begin with `<namespace>.` and must be unique across both lists. Helper
names must match `[a-z][a-z0-9_]*` and be unique. Declarations are immutable for the lifetime of
the process.

An omitted `outputs` keeps the step result open for compatibility. In a schema, `{}` is a scalar,
`{"fields": {...}}` is a closed object, `{"open": true, "fields": {...}}` allows additional object
keys, and `{"items": {...}}` is an array with the given element schema. Wuko uses declared schemas
to validate references such as `steps.build.status` before execution.

For an executor, `cancel_stops_process` declares whether canceling `executor.run` also stops the
underlying command. Set it to false only when cancellation returns control to Wuko but the remote
command can continue running.

## Method reference

Every method except `cancel` is a request and requires one final response.

| Method | Parameters | Successful result |
| --- | --- | --- |
| `initialize` | `protocol`, optional `host_version` | Protocol, namespace, and declarations described above. |
| `plugin.start` | `with` | `{}` |
| `plugin.stop` | `reason` | `{}` |
| `helper.call` | `name`, `args` | `{"value": <JSON value>}` |
| `step.validate` | `type`, `with`, `context` | `{}` |
| `step.run` | `type`, `with`, `context` | Step result. |
| `step.cleanup` | `type`, `with`, `result` | `{}` |
| `executor.validate` | `type`, `with`, `context` | `{}` |
| `executor.open` | `type`, `with`, `context` | `{"session":"<non-empty id>"}` |
| `executor.run` | Session and process parameters | Process result. |
| `executor.close` | `session` | `{}` |
| `shutdown` | none | `{}` |
| `cancel` | `id` | No response; this is a notification. |

### Lifecycle methods

If initialization returned `"lifecycle": true`, Wuko sends `plugin.start` once, immediately before
the first runtime operation:

```json
{"id":"2","method":"plugin.start","params":{"with":{"mode":"strict"}}}
```

`with` is the configuration from the authoritative workflow declaration. It is an empty object for
an ambient local plugin. Validation and installation handshakes do not start the lifecycle.

At teardown Wuko sends `plugin.stop` only if the lifecycle started successfully:

```json
{"id":"12","method":"plugin.stop","params":{"reason":"completed"}}
```

`reason` is `completed`, `failed`, or `canceled`. Wuko then sends `shutdown`, whether or not the
plugin uses lifecycle methods. After answering `shutdown`, the plugin should exit with status zero.

### Helpers

```json
{"id":"3","method":"helper.call","params":{"name":"slug","args":["Hello World"]}}
{"id":"3","result":{"value":"hello-world"}}
```

`args` contains JSON-compatible values. The plugin validates their number and types. The `value`
wrapper is required, including when the value itself is `null`.

### Steps

Validation and execution receive the same shape:

```json
{
  "id": "4",
  "method": "step.run",
  "params": {
    "type": "acme.uppercase",
    "with": {"value": "hello"},
    "context": {
      "step_id": "greeting",
      "workflow_name": "example",
      "workflow_dir": "/work/example",
      "run_dir": "/work/example",
      "vars": {},
      "inputs": {},
      "env": {"CI": "true"},
      "steps": {},
      "dependencies": {},
      "attempt": 1,
      "max_attempts": 1,
      "operation_id": "opaque-operation-id"
    }
  }
}
```

`with` is the rendered configuration for the step. Context collections contain JSON-compatible
workflow state and should be treated as read-only snapshots. JSON numbers retain their lexical
representation across the protocol; implementations decoding into `any` should use their JSON
library's lossless-number mode rather than converting every number to a binary floating-point
value.

A step returns outputs and optional workflow-variable writes:

```json
{"id":"4","result":{"outputs":{"value":"HELLO"},"variables":{}}}
```

Both fields may be omitted when empty. When a step declared `cleanup: true`, every successful run
is paired with one later cleanup request. Cleanup receives that run's result:

```json
{
  "id": "11",
  "method": "step.cleanup",
  "params": {
    "type": "acme.temporary",
    "with": {"directory": "build"},
    "result": {"outputs": {"path": "/tmp/item"}, "variables": {}}
  }
}
```

Cleanup may run after workflow cancellation, so it must bound its own external operations.

### Executors

Validation and session creation receive this context:

```json
{
  "id": "5",
  "method": "executor.open",
  "params": {
    "type": "acme.remote",
    "with": {"host": "build.example.com"},
    "context": {
      "workflow_name": "example",
      "run_dir": "/work/example",
      "env": {"CI": "true"}
    }
  }
}
```

The plugin returns an opaque session ID. Wuko may run several commands through the session before
closing it.

```json
{"id":"5","result":{"session":"session-1"}}
```

An executor command request is:

```json
{
  "id": "6",
  "method": "executor.run",
  "params": {
    "session": "session-1",
    "command": "printf",
    "args": ["hello"],
    "dir": "/work/example",
    "env": {"CI": "true"},
    "stdin": "",
    "capture_limit": 1048576,
    "stdout_policy": 0,
    "stderr_policy": 0
  }
}
```

`stdin` is base64-encoded bytes. `capture_limit` is the maximum captured byte count per stream;
zero means unlimited. Output policies are numeric protocol-v1 values:

| Value | Name | Stream events | Return captured text |
| --- | --- | --- | --- |
| `0` | tee | Yes | Yes |
| `1` | inherit | Yes | No |
| `2` | capture | No | Yes |
| `3` | discard | No | No |

Return the command result using snake_case fields:

```json
{
  "id": "6",
  "result": {
    "stdout": "hello",
    "stderr": "",
    "exit_code": 0,
    "stdout_truncated": false,
    "stderr_truncated": false
  }
}
```

Wuko applies the requested capture policy and limit again to the returned result. A nonzero
`exit_code` becomes a normal process-exit error. Close the session by releasing its resources and
returning `{}`:

```json
{"id":"10","method":"executor.close","params":{"session":"session-1"}}
```

Protocol v1 does not support TTYs, interactive exchanges, streaming stdin, native task graphs, or
executor filesystem access.

## Ordering and lifecycle

Wuko owns one process per namespace for the complete command. The typical order is:

```text
launch
  initialize
  zero or more validation calls
  plugin.start                    only when lifecycle=true and runtime work begins
  helper.call / step.run / executor.open
  executor.run
  executor.close
  step.cleanup                    successful cleanup-enabled runs, in host cleanup order
  plugin.stop                     only after a successful plugin.start
  shutdown
exit
```

Operations from concurrent workflow branches may overlap, and final responses may be returned in
any order. `plugin.start` is serialized and called at most once. Wuko closes executor sessions and
runs step cleanup before `plugin.stop`.

## Limits and failure behavior

- Each request or plugin-output line is limited to 10 MiB, including its JSON envelope.
- Standard output must contain protocol frames only; an ordinary log line is a malformed frame.
- Standard error is forwarded as plugin diagnostics and is not parsed as protocol data.
- Unknown response IDs and malformed response or event envelopes fail every pending request.
- Wuko requires exactly one of `result` and `error` in a response.
- On cancellation, Wuko stops forwarding events for that request immediately.
- Shutdown calls are bounded. A plugin that does not exit is sent `SIGTERM`, then forcibly killed.
- All values crossing the protocol must be valid JSON values. Binary stdin and streamed output use
  base64 because JSON strings are not a byte container.

## Versioning

The protocol identifier is `wuko.plugin/v1`. Additive operation-specific result fields may be
ignored by Wuko, but top-level frame envelopes are strict. A future incompatible wire format must
use a new protocol identifier; plugin package versions do not change protocol selection.
