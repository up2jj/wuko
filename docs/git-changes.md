# Git changes and policy recipes

[Back to the available steps](../README.md#available-steps)

`git_diff` turns Git changes into structured workflow data. `git_diff_check` applies Git's native
whitespace and conflict-marker checks without shell scripts. They work together with ordinary Wuko
conditions, assertions, fan-out controls, and reporting steps.

## Choose the source

| Question | Use |
| --- | --- |
| What am I about to commit? | `git_diff` with `source: staged` |
| Are staged changes safe to commit? | `git_diff_check` with `source: staged` |
| What tracked work have I not staged? | `git_diff` with `source: unstaged` |
| What differs from the main branch or a release? | `git_diff` with `source: commit` |
| Does every outgoing commit pass Git checks? | `git_diff_check` with `source: pushed` |
| Where did two branches diverge? | [`git_merge_base`](steps-system.md#git_merge_base) |
| Which commits produced the change? | [`git_log`](steps-system.md#git_log) |
| What metadata belongs to one commit? | [`git_revision`](steps-system.md#git_revision) |

A commit diff with `from` and `through` compares the two endpoint trees. Changes introduced and
then removed between those endpoints are invisible. A pushed check deliberately behaves
differently: it validates every introduced commit, so an intermediate error cannot hide behind a
later cleanup commit.

See the [`git_diff`](steps-system.md#git_diff) and
[`git_diff_check`](steps-system.md#git_diff_check) references for every field and output.

## Local feedback and Git hooks

### Reject whitespace errors before commit and push

The workflow generated by `wuko git hook init` uses two shell-free targets:

```yaml
version: 1
name: git-check
targets:
  staged:
    steps:
      - id: whitespace
        type: git_diff_check
        with: {source: staged}
  pushed:
    steps:
      - id: whitespace
        type: git_diff_check
        with: {source: pushed}
```

The pushed target reads the active pre-push payload. It handles several ref updates, new and
deleted branches, commits shared by more than one ref, and root commits. It skips merge commits,
which carry no changes of their own; the staged target already checks a conflict resolution when it
is committed. Restrict either check with
Git pathspecs when generated or vendored paths follow different whitespace rules:

```yaml
- id: source_whitespace
  type: git_diff_check
  with:
    source: staged
    paths: [src, tests]
```

### Review unstaged work before staging it

```yaml
- id: unstaged
  type: git_diff
  with: {source: unstaged}

- id: review
  type: tui_table
  with:
    message: Unstaged tracked changes
    from: steps.unstaged.files
    columns:
      - {header: Status, field: status, width: 14}
      - {header: Path, field: path}
      - {header: Added, field: additions, width: 8}
      - {header: Removed, field: deletions, width: 8}
```

Interactive review belongs in a manually run workflow. Git-hook workflows are deliberately
non-interactive.

## Selective tests and builds

### Run checks only for affected components

Read the diff once and reuse it for several monorepo components:

```yaml
- id: changes
  type: git_diff
  with: {source: staged}

- id: api_tests
  type: shell
  if: any(steps.changes.files, {hasPrefix(.path, "services/api/")})
  with: {command: go, args: [test, ./services/api/...]}

- id: worker_tests
  type: shell
  if: any(steps.changes.files, {hasPrefix(.path, "services/worker/")})
  with: {command: go, args: [test, ./services/worker/...]}

- id: frontend_tests
  type: shell
  if: any(steps.changes.files, {hasPrefix(.path, "frontend/")})
  working_directory: frontend
  with: {command: npm, args: [test]}
```

The same pattern can selectively:

- run dependency audits when `go.mod`, `go.sum`, `package.json`, or a lockfile changes;
- build a container when its service directory, `Dockerfile`, or shared base image changes;
- validate Terraform, Kubernetes, or Helm only when deployment files change;
- run integration tests when application code, fixtures, or test infrastructure changes;
- refresh a component cache only when that component's inputs change.

When only one component matters, let Git filter before Wuko builds the result:

```yaml
- id: api_changes
  type: git_diff
  with:
    from: origin/main
    through: HEAD
    paths: [services/api, packages/contracts]
```

### Use a documentation-only fast path

```yaml
- id: changes
  type: git_diff
  with:
    from: origin/main

- id: compile
  type: shell
  if: any(steps.changes.files, {!hasPrefix(.path, "docs/") && !hasSuffix(.path, ".md")})
  with: {command: go, args: [test, ./...]}
```

### Process changed files individually

```yaml
- id: changed_files
  foreach:
    items: filter(steps.changes.files, {.status != "deleted" && hasSuffix(.path, ".go")})
    max_concurrency: 1
    steps:
      - id: check
        type: shell
        with:
          command: ./check-go-file
          args: ["{{ .foreach.item.path }}"]
```

Passing a path as an argument avoids constructing shell source from a filename. Use this pattern for
formatters, linters, generators, and repository-specific checkers.

## Repository policy

### Require companion files

Require a migration when a data model changes:

```yaml
- id: migration_policy
  type: assert
  with:
    expr: |
      !any(steps.changes.files, {hasPrefix(.path, "internal/models/")}) ||
      any(steps.changes.files, {hasPrefix(.path, "migrations/")})
    message: Database model changes require a migration
```

Companion-file policies also cover:

- a dependency manifest and its lockfile;
- protobuf, OpenAPI, or GraphQL schemas and checked-in generated clients;
- public API code and its documentation;
- production code and repository-required tests or fixtures.

These are repository conventions based on paths. They do not prove that generated output is fresh
or that tests cover the changed behavior; run the relevant generator or test when that proof is
required.

### Protect sensitive or required paths

```yaml
- id: protected
  type: assert
  with:
    expr: |
      !any(steps.changes.files, {
        .path == ".env" || hasPrefix(.path, "private/")
      })
    message: The change contains a protected path

- id: required_files
  type: assert
  with:
    expr: |
      !any(steps.changes.files, {
        .status == "deleted" && .path in ["CODEOWNERS", "SECURITY.md"]
      })
    message: The change deletes a required repository file
```

A protected-path rule is not a secret scanner: it does not inspect file contents.

### Detect mode and submodule changes

```yaml
- id: executable_policy
  type: assert
  with:
    expr: |
      !any(steps.changes.files, {
        .old_mode != "100755" && .new_mode == "100755"
      })
    message: The change unexpectedly makes a file executable

- id: submodule_review
  type: assert
  with:
    expr: '!any(steps.changes.files, {.new_mode == "160000"})'
    message: Submodule pointer changes require explicit review
```

### Keep changes reviewable

```yaml
- id: review_budget
  type: assert
  with:
    expr: |
      steps.changes.count <= 100 &&
      steps.changes.additions + steps.changes.deletions <= 2000 &&
      steps.changes.binary_files <= 5
    message: Change exceeds the repository review budget
```

Git does not return line totals for binary files, so budget them separately. Rename detection also
prevents a pure move from looking like a full deletion and addition. Use `previous_path`, `path`,
and `score` when moves affect ownership or package-boundary rules.

## CI, releases, and maintenance

### Determine pull-request or release scope

```yaml
- id: release_diff
  type: git_diff
  with:
    from: v2.3.0
    through: HEAD
```

The same endpoint comparison can determine affected pull-request components, decide which release
artifacts to package, verify a maintenance backport, or drive component-specific versioning. Use
`git_merge_base` when CI supplies two branch tips rather than an already verified boundary.

Use `git_diff` for the final repository state and `git_log` when release notes also need the commits
and their Conventional Commit classifications:

```yaml
- id: files
  type: git_diff
  with: {from: v2.3.0, through: HEAD}

- id: commits
  type: git_log
  with: {after: v2.3.0, through: HEAD, merges: exclude}
```

### Require Conventional Commits on pull requests

Keep the policy in `.wuko/workflows/conventional-pr-commits.yaml`. Declared revision variables make
the same workflow valid and runnable locally instead of coupling it to the GitHub execution
context:

```yaml
version: 1
name: conventional-pr-commits
description: Require Conventional Commit messages on pull requests
vars:
  base: ""
  head: ""
steps:
  - id: branch_point
    type: git_merge_base
    with:
      from: "{{ .vars.base }}"
      through: "{{ .vars.head }}"

  - id: commits
    type: git_log
    with:
      after: "{{ .steps.branch_point.sha }}"
      through: "{{ .vars.head }}"
      merges: exclude
      limit: 1000

  - id: complete_history
    type: assert
    with:
      expr: "!steps.commits.has_more"
      message: Pull request contains more than 1000 commits

  - id: validate_commits
    foreach:
      items: steps.commits.commits
      max_iterations: 1000
      steps:
        - id: conventional
          type: assert
          with:
            expr: foreach.item.conventional.valid
            message: 'Commit {{ .foreach.item.short_sha }} is not conventional: {{ .foreach.item.subject }}'
```

Wire it to `.github/workflows/conventional-commits.yml`. Replace `<VERSION>` with a pinned Wuko
release that contains `git_merge_base`:

```yaml
name: Conventional commits
on:
  pull_request:

permissions:
  contents: read

jobs:
  conventional-commits:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0

      - name: Validate PR commits
        uses: up2jj/wuko@<VERSION>
        with:
          workflow: conventional-pr-commits
          vars: |
            {
              "base": ${{ toJSON(github.event.pull_request.base.sha) }},
              "head": ${{ toJSON(github.event.pull_request.head.sha) }}
            }
```

The merge base prevents commits added only to a moving base branch from entering the PR range.
Merge commits are excluded, while autosquash and other non-conventional subjects fail with the
offending commit ID. Run the identical policy locally before pushing:

```sh
wuko run conventional-pr-commits --once --var base=origin/main --var head=HEAD
```

### Inspect every commit independently

```yaml
- id: history
  type: git_log
  with:
    after: v2.3.0
    merges: exclude

- id: commit_diffs
  foreach:
    items: steps.history.commits
    collect: '{"sha": foreach.item.sha, "files": steps.diff.files}'
    steps:
      - id: diff
        type: git_diff
        with:
          through: "{{ .foreach.item.sha }}"
```

Without `from`, every commit is compared with its first parent. Use this for commit-level audit or
release records. Prefer one endpoint comparison when only the final branch state matters.

### Pass a normalized summary to another workflow or process

`git_diff` outputs are ordinary YAML/JSON-compatible data. They can feed workflow outputs, `set`,
`process_call`, or serialization helpers without parsing Git's terminal output. This is useful for
change summaries, affected-component indexes, cache invalidation inputs, and later reporting
integrations.

## Boundaries

- Untracked files do not appear in staged or unstaged diffs until Git adds them to the index.
- Git path restrictions use pathspec semantics, not Wuko glob syntax.
- The steps do not fetch remotes. Remote comparisons use locally available objects and refs.
- New-branch push enumeration excludes commits already reachable from local remote-tracking refs.
- Binary files have no additions or deletions; use `binary` and `binary_files`.
- Rename and copy detection are Git heuristics. `score` reports Git's similarity percentage.
- Explicit `from` and `through` values compare endpoint trees and may be divergent.
- Path policies do not inspect content and do not replace linters, generators, tests, or security
  scanners.
